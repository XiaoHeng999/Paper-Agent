# Paper-Agent 的多 Agent 边界与恢复方案

讨论记录，2026-11-21。现状以提交 `7d1c958` 为基线。下文的实施顺序和验收条件供后续研究。

## 从一次核查中断看架构

假设学生已经等到了整篇论文的总结、方法演算和教学图，最后一次核查调用却超时了。对学生来说，合理的下一步是继续核查同一份讲解。若恢复时重新生成总结，箭头顺序、论证措辞甚至教学例子都可能改变。此时即使新报告同样通顺，也很难解释上次究竟审到了哪里。

当前代码已能保留部分待审结果，但 `synthesize` 在一次函数执行中生成草稿、请求核查并应用发布规则。进入核查前，写入内存中待审结果的动作显式排除了候选图边。完整的候选边在这次调用的草稿对象中；工作流等逐篇综合结束后才保存汇总的研究推理产物。这就是优先建立独立草稿边界的实际理由。[综合与核查](../src/research/reasoning.py) · [研究节点](../src/research/workflow.py)

## 讨论形成的判断

自然语言适合写解释和反驳。把它当交接的唯一载体时，下游很难判断某个遗漏究竟来自作者、阅读者还是上下文预算。即使声明 `summary: str`，也找不回摘要中已经丢失的基线。以 Sol-Attn 为例，“加速约五倍”要能追溯到完整系统的初始配置；单独加入该方法的增量另有比较起点。因此，一次可审查的交接要同时提供主张、适用条件、原始证据位置和版本，并允许核查者重新读取原文。[引用边界案例](argumentation-and-insights.md)

临时 Subagent 适合探索开放问题，例如请独立读者尝试找出最强反例。稳定模块适合反复发生、能定义输入输出和失败含义的工作，例如核查某一版主张。后者可以先用普通函数实现。只有出现独立调度、恢复或发布的实际需求，才值得引入子图或服务。对于本项目，搜索具有独立工具和失败模式，逐篇阅读具有自然的并行单位，核查具有独立的判断责任。总结、方法讲解和洞见需要保持同一条论证链。跨篇比较继续由用户的任务范围决定。[现有角色和交接设计](multi-agent-architecture.md)

| 边界 | 已有工程依据 | 后续研究重点 |
| --- | --- | --- |
| 上下文 | 单篇任务在构造模型消息前按论文范围筛选证据。核查可以回查原文。 | 恢复时记录实际选入及遗漏的片段，确保核查者能重建当时的材料。 |
| 权限 | 模型可以提出证据缺口，编排器检查授权和预算后才执行外查。 | 逐步缩小节点可接触的服务句柄，单篇核查接口只接收其所需的证据读取能力。 |

| 失败恢复 | 已支持主张定向修订、部分检索续跑及有条件的结果复用。 | 让最终核查失败后可以从完整草稿恢复；区分超时、预算耗尽和凭据拒绝。 |

| 控制权 | 模型提议内容和核查意见，程序决定检索、比较及发布。 | 将发布规则抽成可回放的确定性步骤，使一次降级能追溯到原始候选及核查理由。 |

## 建议的实施顺序

### 1. 先让一篇论文的完整草稿能够独立复审

复用现有会话产物仓储。综合完成且通过结构及引用范围校验后，立即保存完整草稿，再发起核查。未审草稿与读者可见报告分别保存，尤其保留最终未发布的边。第一版以整篇复审为单位，同一轮仍可批量核查多条判断。[现有产物仓储](../src/research/storage.py)

| 记录 | 唯一负责写入的步骤 | 下游可依赖的内容 |
| --- | --- | --- |
| 综合草稿 | 综合 | 不可变草稿版本、研究问题、主论文及获准的外证范围、完整候选内容、所选证据 ID 与版本、生成策略版本。 |
| 核查记录 | 核查 | 草稿版本、核查策略版本、逐项裁决、理由、核查所用证据。对象索引须绑定草稿版本，防止新版重排后错配。 |
| 发布记录 | 发布 | 草稿与核查记录的版本、采用或省略的对象、原因、发布规则版本。Markdown 与网页消费同一结果。 |

恢复时先验证依赖。如果草稿有效而核查未完成，沿用草稿和证据重审；已有匹配核查时直接执行发布；来源或用户任务范围改变时重新评估相应草稿。相同版本的重复恢复应产生同一份有效结果。中断发生在模型返回和结果落盘之间时，允许重试调用，但只能接受一份匹配版本的裁决。凭据拒绝应保留可恢复状态，待凭据或额度恢复后再发起请求。旧报告仍可阅读，缺少完整草稿的历史任务走既有重算路径。

**首个验收实验。** 用 Sol-Attn 固定同一份输入，在草稿落盘后让核查超时，再从会话恢复。记录角色调用次数：恢复期间搜索、阅读、综合均为零次，核查一次。再对同一已完成任务重复恢复，模型调用为零次。检查最终图仍能从每条已发布边追到候选边和原文，省略边也能找到裁决。故障实验可先用固定模型响应复现。

### 2. 收紧来源准备到阅读的交接

保留搜索的论文元数据输出，由来源准备步骤产出明确的逐篇阅读输入。最小字段包括论文身份、来源版本、材料状态、可读片段或原件引用、未覆盖范围和获取失败原因。正文和页图由引用按需读取，避免在多个对象中复制整篇论文。先在现有 `read_results` 边缘加适配与校验，再迁移消费者；用历史 checkpoint 做兼容测试。[当前共享状态](../src/graph/state_models.py) · [原文加载](../src/research/storage.py)

**验收。** 分别输入只有摘要、已有完整正文、文件已变化、解析失败四种材料。报告应能区分“材料未取得”“本轮尚未覆盖”和“已核查但证据不足”。单篇核查收到另一篇论文的片段 ID 应在调用模型前失败。关闭外部补搜时，模型即使提出有效缺口，检索服务调用次数也应为零。

### 3. 根据依赖拆分版本，再决定是否细化调度

先记录每阶段耗时、模型调用数及复用失败原因，再把生成、核查、发布的策略版本分别纳入相应依赖。共享的证据选择逻辑发生变化时，所有实际依赖它的阶段都应失效。第一步可以保留保守的全局失效兜底，待测试覆盖后逐步缩小。这样能量化节省了多少重算，也能发现误用了过期判断的情况。[现有策略版本和依赖检查](../src/research/incremental.py)

| 变更或故障 | 预期最小执行范围 |
| --- | --- |
| 仅调整网页排版 | 在同一发布结果上重新渲染，模型调用为零。 |
| 修改教学图发布规则 | 用相同草稿与裁决重新发布，并保留之前版本。 |
| 更换核查标准 | 复用符合当前输入范围的草稿，重新核查和发布。 |
| 原文中的图表或实验条件发生变化 | 使依赖变化证据的判断及其下游结果失效；用未改动论文作复用对照。 |

## 下一次研究要回答的问题

建议以“核查超时后只重审”为第一个小版本，比较恢复耗时、重复的模型调用次数、错误复用次数和前后报告的证据可追溯性。若整篇复审仍占主要成本，再用同一份草稿测量逐项复审的收益。逐项方案还要验证跨对象依赖，例如某段机制讲解被降级后，依赖它的洞见是否同步降级。只有这些数据表明调度粒度构成瓶颈，才有充分理由继续拆分。

## 实施记录

单篇综合现在按依赖写入三种会话产物。通过结构和来源检查的完整草稿保存为 `reasoning_draft`，包括候选箭头、选段和遗漏清单。独立核查返回的原始裁决在发布规则应用前保存为 `reasoning_review`。最终 `reasoning_publication` 记录使用的草稿版本、裁决版本和发布策略。SQLite 按会话、阶段和依赖键接受首份有效记录，重试者使用已接受的内容。并发请求仍可能在结果入库前产生模型费用。[阶段编排](../src/research/reasoning.py) · [模型调用](../src/research/synthesis_tasks.py) · [发布规则](../src/research/publication.py)

来源准备将旧阅读条目转换为 `PreparedPaper`，记录论文身份、材料类型、取得状态、失败原因、来源版本、可读证据编号及未读取的候选图页。研究报告保留这些输入。会话在最终综合前保存阅读卡和论证计划的恢复现场，继续任务时重新检查来源、任务范围与版本。已产生草稿但最终核查失败时，研究面板提供“继续核查已保存的草稿”，请求绑定当前报告。整任务意外中断时继续使用会话的恢复入口。[工作流](../src/research/workflow.py) · [会话恢复接口](../src/services/research.py)

可在报告的 `role_stats` 查看每种模型调用的次数及累计请求耗时，在 `recovery_trace` 查看各篇草稿、核查与发布的匹配情况。共享阅读策略或来源版本变化时保守失效。整篇综合仍是最终复审单位；跨篇关系和综述正文继续沿用原有调度策略。持久恢复需要会话仓储，历史报告缺少新增记录时按原流程处理。

回归测试从会话恢复入口覆盖核查超时、重复恢复、原文变化、仅变更核查或发布策略，并检查并发接受同一记录。Sol-Attn 固定响应回放保留 9 条候选边与 9 条原始裁决，最终展示 8 条。该实验测量故障后的工作范围，未重新请求在线模型。[恢复回归测试](../test/test_research_recovery.py)
