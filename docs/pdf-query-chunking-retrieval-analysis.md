# PDF 阅读链路中的 Topic、Query、解析、切分与检索问题分析

本文整理当前 Paper-Agent 在指定论文或 PDF 阅读场景中的输入来源、处理链路和主要问题。重点讨论四组相互关联的问题：`topic` 字段的语义过载、运行时 query 的语义过载、PDF 解析能力不足，以及文档切分与检索缺少结构和关系感知。

本文是对现状的分析，不表示当前系统完全不可用。现有实现优先保证来源可追溯、页码可定位、证据有版本、图像可回看和失败可显式记录；主要不足在于深层文档理解和 query 驱动的阅读规划仍然较弱。

## 1. 核心结论

当前流程不是“只有 PDF，也没有 query”，而是要求一次研究请求同时包含：

- `topic`：来自用户发送的会话文本，表示研究主题或阅读任务；
- `constraints.papers`：可选的指定论文列表，其中可以包含 `pdf_url`；
- 其他约束：报告形式、是否允许跨篇分析、视觉页预算等。

主 query 不是由上一个 Agent 自动生成的。会话消息的 `content` 会被直接保存为 `ResearchRequest.topic`，并在后续阅读、召回、核查和写作阶段反复使用。

如果用户没有指定论文，Search Agent 会根据 `topic` 生成子主题和论文数据库检索式；如果用户已经指定论文或 PDF，工作流会跳过 Search Agent，直接进入阅读节点。因此，指定 PDF 场景目前缺少一个专门的 Reading Planner 来拆解问题和制定阅读计划。

当前系统的总体形态可以概括为：

```text
用户 topic + 可选指定论文/PDF
        ↓
PDF 文本抽取与固定切分
        ↓
使用 topic 对既有 chunk 做优先召回
        ↓
Reader 从分批证据中抽取 claims
        ↓
Reader / Verifier 后置生成核心问题、反证查询和修复查询
        ↓
生成可追溯但可能覆盖不完整的报告
```

因此，当前系统已经使用 query，但 query 介入得较晚：它不参与 PDF 的结构化解析和初始切分，主要在切分完成后用于排序、召回、模型提示和核查。

## 2. Topic 和 Query 的来源

### 2.1 主 topic 来自用户输入

前端文本框要求用户输入“研究主题或调研任务”。后端将该文本直接构造成：

```python
ResearchRequest(
    topic=content,
    constraints=constraints,
)
```

`ResearchRequest.topic` 因此是用户原始输入，不是 Search Agent、Reader 或其他上游 Agent 自动生成的内容。

例如一次指定论文请求在逻辑上相当于：

```json
{
  "content": "分析这篇论文的核心方法、实验结果和局限",
  "constraints": {
    "papers": [
      {
        "id": "paper-1",
        "title": "Example Paper",
        "pdf_url": "https://example.org/paper.pdf"
      }
    ]
  }
}
```

其中：

- `content` 进入 `request.topic`；
- `papers` 确定阅读对象；
- `pdf_url` 只负责提供全文来源，本身不等于研究问题。

相关入口包括：

- `src/services/paper_workflow_runtime.py`
- `src/agents/contracts.py`
- `front/src/components/session/SessionComposer.vue`

### 2.2 指定论文时跳过 Search Agent

如果请求包含 `constraints.papers`，这些论文会直接进入 `search_results`，并设置 `supplied_papers=True`。图入口随后从阅读节点开始，不运行 Search Agent。

```text
未指定论文：topic → Search Agent → 搜索论文 → Reader → Research

指定论文：topic + papers/PDF → Reader → Research
```

这说明 Search Agent 生成的子主题和英文关键词只服务于“找到论文”，不负责“如何阅读已经给出的论文”。

相关路由位于：

- `src/graph/graph.py`
- `src/agents/searchAgent.py`

### 2.3 后续 Agent 会派生新的内部 query

虽然主 topic 来自用户，系统在后续阶段还会生成多种内部 query：

| Query 类型 | 生成者 | 主要用途 |
| --- | --- | --- |
| 主研究 topic | 用户 | 初始召回、论文阅读、比较和报告写作 |
| 文献数据库检索式 | Search Agent | 未指定论文时搜索候选论文 |
| 核心问题 | Reader | 从已抽取 claims 中选择最多两个重点问题 |
| 核查查询 | Verifier 流程 | 使用 claim statement 搜索局限、失败、消融和反例 |
| 修复查询 | Verifier | 判断被限定或反驳后定向重读证据 |
| 证据缺口查询 | Argument Planner | 判断是否需要本地补读或外部论文佐证 |

因此，不能笼统地说“系统没有 query”。更准确的描述是：系统存在多个 query，但没有清晰区分它们的职责、结构和生命周期。

## 3. Topic 字段的语义过载

`request.topic` 是一个单独的字符串，但当前被同时用于：

1. 表示用户的研究目标；
2. 生成论文搜索计划；
3. 判断摘要与主题是否相关；
4. 作为全文向量召回 query；
5. 指导 Reader 抽取 claims；
6. 指导视觉候选页排序；
7. 指导跨论文比较；
8. 指导最终报告写作。

这些任务对输入的要求并不相同。例如：

```text
“全面阅读这篇论文”
```

可以作为任务指令，但不是一个有效的语义检索 query。相反：

```text
“该方法的推理延迟优势在何种硬件、batch size 和精度约束下成立”
```

适合作为证据检索问题，却不一定适合作为论文数据库的宽范围搜索式。

### 3.1 Topic 过载带来的影响

- 泛化任务指令被直接用于向量召回，召回结果缺少判别力；
- 搜索论文、阅读论文和核查主张共享同一个字符串，无法为不同阶段优化；
- 无法显式表达开放式阅读、定向问答、复现审查、实验比较等不同任务模式；
- 恢复任务时会沿用原始 topic，后续派生问题与主问题之间缺少统一的可追踪结构；
- 报告可能响应了某些后置生成的问题，却没有清楚说明它们与用户原始意图的关系。

### 3.2 PDF-only 场景定义不清

当前标准前端流程要求文本输入非空，API 数据结构也要求构造 `ResearchRequest.topic`。因此，严格意义上的“只上传 PDF、不提供任何任务”没有被正式建模。

调用方可能使用以下占位 topic：

```text
read
阅读这篇论文
总结论文
```

系统仍然能够运行，因为 Reader 的通用提示会抽取研究问题、方法、结果、实验条件和局限。但此时 topic 驱动的向量召回和视觉排序几乎失去针对性，流程会退化为“通用论文抽取 + 后置聚焦”。

## 4. Query 的语义过载与阅读规划不足

Topic 过载主要是输入字段设计问题；query 过载则是运行时检索和推理问题。当前多个阶段都使用自然语言字符串作为 query，但缺少统一的 query 对象来记录：

- query 的来源；
- query 的目标阶段；
- query 对应的子问题；
- 需要什么类型的证据；
- 已找到和仍缺失的证据；
- query 与原始用户问题的关系；
- query 是否已完成、失败或被修订。

### 4.1 缺少指定 PDF 的前置 Reading Planner

当前 Search Agent 能把主题拆成论文检索子方向，但指定论文时会被跳过。Reader 的核心问题又是在读取部分证据并生成 claims 之后才产生。

当前顺序是：

```text
先切分和读取部分证据
    ↓
生成 claims
    ↓
从已有 claims 中挑选核心问题
```

这会造成首批证据偏差：如果初始召回不准确，后续核心问题也可能被错误的局部内容带偏。

更理想的顺序应当是：

```text
理解用户任务和论文基本结构
    ↓
拆分可验证的阅读子问题
    ↓
为每个子问题声明所需证据
    ↓
定向读取章节、段落、公式、图表和附录
```

### 4.2 初始 query 缺少证据需求表达

例如用户问：

```text
为什么该方法比 Transformer 更快，同时保持准确率？
```

这至少需要拆成：

1. 方法机制有什么变化；
2. 理论复杂度是否降低；
3. 实际 latency 或 throughput 是否改善；
4. 比较使用了什么硬件、batch size 和数值精度；
5. 准确率比较是否使用相同数据、预算和基线；
6. 哪些消融实验能够归因于目标模块；
7. 是否存在失败场景和适用范围。

当前系统主要把原始 topic 直接用于向量召回，再依赖模型 Prompt 在阅读时隐式完成这些拆解。问题拆解没有成为一个可保存、可检查、可逐项完成的中间产物。

## 5. PDF 解析问题

### 5.1 当前文本解析方式

当前默认使用 `pypdf.PdfReader` 逐页调用 `extract_text()`，随后做轻量清洗并写入 `paper.md`。每页之间插入：

```markdown
<!-- page: 3 -->
```

该设计能够保留页码并支持来源追踪，但它不是版面理解或学术文档结构解析。

相关代码位于：

- `src/utils/read_utils/pdf_parsers.py`
- `src/utils/read_utils/read_fulltext.py`

### 5.2 文本读取的主要风险

- 双栏论文的阅读顺序可能错乱；
- 页眉、页脚、脚注可能混入正文；
- 跨页段落可能被割裂；
- 数学公式可能丢失、乱码或顺序错误；
- 表格可能退化为无法恢复行列的文本；
- 图注与图像、表注与表格缺少对象级关联；
- 章节标题和正文层级不能可靠恢复；
- 字体编码或嵌入字符异常可能导致文本不可读。

### 5.3 扫描 PDF 的覆盖不完整

当页面文本很少或图片面积很大时，系统会将其视为扫描页候选，并把选中的整页渲染为 PNG 交给视觉模型转录。该机制存在以下限制：

- 视觉页是预算内抽样，不是完整 OCR；
- 未被选中的扫描页可能完全没有可用文本；
- 视觉转录依赖模型，没有独立 OCR 结果做交叉校验；
- 密集表格、公式和低分辨率页面容易转录错误；
- 页面级转录仍然没有恢复图表、公式和段落之间的结构关系。

### 5.4 图像解析是页面级而不是对象级

当前系统主要识别“哪些页可能含有图表或扫描内容”，然后渲染整页。它没有稳定提取：

- 单个 Figure 的边界；
- Figure 与 Caption 的绑定；
- 表格单元格结构；
- 图例与曲线关系；
- 坐标轴、误差条和数据点；
- 正文中对公式、图表和附录的引用关系。

这使得视觉核查可以确认某页的大致内容，但难以形成细粒度、可复用的结构化视觉证据。

## 6. 文档切分问题

### 6.1 当前切分策略

当前 `PageChunker` 首先按 PDF 页码标记切分；单页内容超过 1200 个字符时，再按固定字符长度硬切。

```text
PDF page
  ↓
超过 1200 字符？
  ├── 否：整页成为一个 chunk
  └── 是：按字符位置切成多个 chunk
```

相关代码位于 `src/utils/read_utils/chunkers.py`。

### 6.2 固定字符切分破坏语义完整性

硬切可能切断：

- 一个句子；
- 一个完整段落；
- 公式与其解释；
- 实验设置与实验结果；
- 方法步骤之间的输入输出关系；
- 图表与图注；
- 表格的行列；
- 结论与紧随其后的限制条件。

当前也没有重叠窗口，因此位于边界附近的限定信息不会自然出现在两个 chunk 中。

### 6.3 Chunk 缺少文档层级

Chunk 的 `section` 通常只是：

```text
page_1
page_2
page_3
```

而不是：

```text
Introduction
Method / Architecture
Experimental Setup
Results
Ablation
Limitations
Appendix
```

因此，系统无法直接利用章节角色判断某个 chunk 更可能包含背景、核心方法、结果还是限制。

### 6.4 Chunk 之间只有弱邻接关系

`TextChunk` 会记录 `previous_chunk_id` 和 `next_chunk_id`，但转换为研究阶段使用的 `EvidenceSpan` 时没有保留这些字段。后续邻居扩展主要依赖证据在容器中的排列位置，简单取前后各一个片段。

这只表达物理顺序，不能表达以下语义关系：

```text
实验结果 → 使用哪个实验设置
消融实验 → 验证哪个方法组件
公式 → 依赖哪些假设
图表 → 支持哪条结论
限制条件 → 限定哪条结果
附录实验 → 补充正文哪一节
```

### 6.5 缺少跨页和跨章节组合

论文中的完整论证经常跨越多个 chunk：方法在前文定义，实验设置在后文说明，主要结果位于表格，限制出现在讨论或附录。当前简单的前后邻居扩展无法稳定恢复这种长距离依赖。

## 7. 检索问题

### 7.1 Query 在切分后才介入

当前顺序是：

```text
PDF → 固定切分 → embedding 索引 → query 召回
```

这意味着 query 无法影响 chunk 的边界和上下文组成。即使用户问的是某个完整实验比较，召回单元仍然可能只是被字符边界截断的局部文本。

### 7.2 初始召回直接使用原始 topic

研究节点首先使用 `request.topic` 做向量检索，并将召回结果放到阅读批次前部。如果 topic 是“阅读这篇论文”或“总结论文”，召回结果不会具有明确的证据方向。

### 7.3 向量召回不是结构化证据召回

当前主要按照 embedding 相似度返回文本片段，缺少系统性的：

- 关键词或 BM25 融合；
- 章节标题加权；
- 图表编号精确匹配；
- 公式编号精确匹配；
- 父章节和子段落扩展；
- citation link 扩展；
- 多 query 召回融合；
- reranker；
- 基于证据类型的覆盖约束。

### 7.4 Top-k 相关不等于证据完整

一个相似度较高的片段可能只包含结果数字，却缺少：

- 数据集；
- 基线版本；
- 指标定义；
- 训练预算；
- 硬件条件；
- 样本量；
- 误差范围；
- 限制和失败场景。

系统会通过相邻片段、关键词扫描和反证查询做补偿，但这些是后置补救，不是以“完整证据包”为目标的检索策略。

### 7.5 阅读批次不是全局文档理解

Reader 分批读取证据，每个调用只看到当前提供的 `EvidenceSpan` 和少量前提/限制锚点。不同批次生成的 claims 之后再合并，可能出现：

- 同一结论重复抽取；
- 跨批次术语含义不一致；
- 前一批结果遗漏后一批出现的限制；
- 局部结果被错误泛化；
- 方法步骤在不同批次中失去连续性。

## 8. 视觉、证据与核查的衍生问题

虽然本文重点是 topic/query、解析、切分和检索，但这些问题会继续传导到视觉和核查阶段。

### 8.1 视觉页选择依赖粗粒度启发式

系统根据页面文字量、图片面积、Figure/Table 标记和少量实验关键词选择视觉候选页，并受到每篇和全局页数预算限制。因此，没有被选中的关键图表可能无法进入视觉核查。

### 8.2 文本与图像主要按页码绑定

当前页码和图像哈希能够保证来源版本一致，但不能细粒度表达：

```text
某个 claim 对应 Table 2 的第三行第五列
某个趋势对应 Figure 3 的红色曲线
某个限定条件来自图注的最后一句
```

### 8.3 核查角色不等于真正独立模型

Reader、Verifier 和视觉转录通常共享同一个研究模型实例，只是使用不同 Prompt。这属于角色和上下文隔离，不等于模型层面的独立验证。

### 8.4 覆盖预算可能被误解为完整阅读

系统受上下文字符数、调用次数、超时、claim 数量和视觉页预算限制。虽然遗漏会被记录，最终报告仍可能被误读为对全文的完整分析。

## 9. 问题之间的因果关系

这些问题不是彼此独立的。主要传导链路是：

```text
Topic 语义过载或过于泛化
        ↓
无法形成明确的阅读子问题和证据需求
        ↓
PDF 只做页级文本抽取，缺少文档结构
        ↓
按页和固定字符切分，破坏语义单元
        ↓
Query 只能召回孤立 chunk
        ↓
Reader 从局部批次中生成 claims 和核心问题
        ↓
后置核查需要反复补救上下文缺失
        ↓
视觉页预算和证据粒度进一步限制核查
        ↓
最终报告可追溯，但深度、覆盖和完整性不稳定
```

因此，单独调整 chunk 大小或提高 top-k 不能从根本上解决问题。上游缺少任务建模和文档结构，下游检索与核查只能不断补救。

## 10. 问题分类汇总

### 10.1 P0：任务和语义建模

- `topic` 同时承担搜索、阅读、召回、核查和写作目标；
- PDF-only 和开放式阅读没有正式任务模式；
- 指定论文时缺少独立 Reading Planner；
- 没有结构化记录子问题、证据需求和完成状态；
- 初始阅读问题依赖用户是否写出了高质量 topic。

### 10.2 P0：文档结构和切分

- PDF 文本没有恢复可靠章节和版面结构；
- 按页及固定字符硬切，可能破坏语义完整性；
- 缺少句子/段落边界和 overlap；
- Chunk 之间缺少语义关系和长距离依赖；
- 图表、公式、表格和正文不能形成统一文档对象。

### 10.3 P1：Query 驱动检索

- Query 在切分后才介入；
- 初始召回直接复用原始 topic；
- 缺少面向子问题的多 query 检索；
- 缺少混合检索、层级扩展和 reranker；
- 检索目标是相关 chunk，而不是条件完整的证据包。

### 10.4 P1：PDF 与视觉解析

- `pypdf` 对双栏、公式和复杂表格不稳定；
- 扫描页没有完整 OCR；
- 视觉读取是预算内整页抽样；
- 缺少对象级图表、表格和坐标结构；
- 文本证据与视觉证据只做页级弱绑定。

### 10.5 P2：推理、验证与产品表达

- 分批 claims 可能存在跨批次不一致；
- 核心问题后置，可能受首批证据偏差影响；
- 独立核查通常仍由同一模型承担；
- 字符预算不能准确等价为 token 预算；
- 有界阅读和完整全文分析之间的产品表达仍不够清晰。

## 11. 后续改进应遵循的方向

后续设计可以围绕以下边界展开，具体方案应另行设计和评审：

1. 将用户任务、论文搜索 query、阅读子问题、证据 query 和报告目标拆成不同对象；
2. 为指定论文和 PDF 增加独立 Reading Planner；
3. 在切分前恢复章节、段落、公式、图表、表格和引用结构；
4. 使用结构感知、语义完整且带适当 overlap 的切分策略；
5. 显式保存 chunk 的父子、邻接、引用和论证关系；
6. 从“召回相似文本”转向“为子问题组装完整证据包”；
7. 将向量、关键词、章节、图表编号和关系扩展组合成混合检索；
8. 将视觉对象与正文引用绑定到图、表、单元格和公式级别；
9. 显式报告已覆盖问题、缺失证据和未读范围；
10. 保留现有的来源哈希、页码、证据 ID、版本失效和失败降级能力。

## 12. 结论

当前 Paper-Agent 的优势是证据可追溯、来源有版本、图像可回看、失败不会被静默包装成成功；其主要限制是文档理解层偏浅。

最核心的问题不是单一的 chunk 太短或 top-k 太小，而是：

> 用户 topic 没有被转化为结构化阅读计划，PDF 没有被转化为结构化学术文档，检索也没有围绕可验证子问题组装完整证据。

因此，topic/query 语义过载、PDF 解析不足、固定切分和孤立 chunk 检索共同形成了当前质量瓶颈。后续改造应优先解决任务建模和文档结构，再改进切分与检索；否则下游 Reader、Verifier 和视觉模型仍需用更多调用去补救上游缺失的信息。
